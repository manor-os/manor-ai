# 工作区与知识

工作区将人员、Agent、文档、任务、工作流和知识组织在一个运营边界之内——通常业务的每个部分对应一个工作区：一处你管理的物业、一个客服收件箱、一项营销职能。

## 界面模式 {#interface-modes}

已有明确选择会保留。尚未选择时，老用户默认使用**专业模式**，不弹首次引导；新用户会看到 **User Guide**，预选**简单模式**，点击**开始**后保存并进入导览。可从**更多 → User Guide** 再次打开，也可在**设置 → 外观 → 界面模式**修改。选择保存在当前浏览器中。

- **简单模式**聚焦聊天和**安装 Workspace**。自托管版通过此入口导入[蓝图](blueprints.md) JSON 文件。工作区聊天仍以只读方式显示 Manor 与各 Agent 的头像、名称和成员数量；必要的运行状态、审批、产物和连接设置仍可访问。
- **专业模式**提供完整的工作区页面、配置操作和详细聊天过程。

切换模式只改变界面展示，不改变权限、执行或数据。已有会话和文字草稿仍可保留。

## 工作区 {#workspaces}

一个工作区界定以下内容的范围：

- Agent 与技能（通过服务映射和订阅）。
- 会话与任务。
- [目标](goals.md)及其执行计划。
- 文档与文件资产。
- 知识来源。
- 集成凭据与[渠道](../integrations/channels.md)。
- 治理规则、权限与审计历史。

在专业模式下，工作区页面包含多个标签页：概览（服务、匹配的 Agent、当前工作、运营评分）、目标、任务、文档、渠道、Agent、活动和设置。工作区聊天具有上下文感知能力：它能看到工作区的服务、目标、Agent 和近期活动，并且可以直接从一条消息启动[工作流](workflows.md)。

在专业模式下，创建工作区是一个引导式的聊天流程——Manor 会帮你填写工作区的用途、服务、人员、渠道和种子知识，然后完成创建。你也可以安装[蓝图](blueprints.md)，从打包好的配置起步。

### 删除工作区 {#deleting-a-workspace}

删除工作区会先将其移入回收站，并在配置的宽限期内保留（默认 30 天），期间
可以恢复。新的工作区工作会立即停止；用户创建的自动化和仍有效的 Workflow
操作授权会被移除。恢复时会重新创建工作区内置运行时计划。宽限期结束后，
后台清理会永久删除其运行时记录、任务、会话、绑定，以及工作区专属的
Knowledge 分组和关联。

Knowledge 文档、文件夹、源文件、版本及其访问控制属于实体，会继续保留。
删除工作区不会删除这些文档，也不会扩大其访问范围：仅成员可见的 Knowledge
在来源工作区移除后仍受限制。可通过 Knowledge 在具备相应资源权限时管理
保留的文件。

## 知识 {#knowledge}

知识系统对文档建立索引，使 Agent 可以引用它们。在专业模式下，将 PDF、Word 和 Excel 文件、Markdown、纯文本、幻灯片或图片上传到**知识**中，并按用途将文档分组为知识库（例如"House Rules"、"Vendor Contacts"、"FAQ"）。将分组附加到工作区后，其中的 Agent 会自动使用它们。

### 共享角色 {#sharing-roles}

在文档或文件夹的 **Share → Add people** 中选择四种角色之一：

- **Viewer（查看者）**可以阅读。
- **Commenter（评论者）**可以阅读和评论。
- **Editor（编辑者）**可以编辑，并向共享文件夹上传文件。
- **Co-owner（共同所有者）**拥有与所有者相同的资源权限，包括对外分享、
  发起签署请求、删除及访问管理。

原来的 **Curator / Access manager** 选项已移除。已有授权中具备编辑能力的
显示为 **Editor**，其实际权限会保留，直到你明确修改或撤销授权。不具备编辑
能力的授权按实际能力显示为 Viewer 或 Commenter。选择 Editor 后会应用标准
编辑权限。

同事需要完整控制权时，在角色菜单中选择 **Co-owner**。原始所有者的归属记录
保持不变。密级限制和必要审批同样适用，临时共同所有者不能创建超出自身授权
期限的授权或分享链接。对外分享链接的配置有效期从审批通过时起算，并受申请
时及审批时的有效授权期限约束。工作区根文件夹改名需要工作区管理权限。
将文档移入回收站会撤销包括共同所有者在内的共享授权及链接；原始所有者或
全局 Knowledge 管理员可以恢复文档，恢复不会重新激活已撤销的授权。

共同所有者发送 PDF 签署请求时，使用自己的已连接邮箱。通过 **Add signer**
添加每位签署人，并分别放置必填签名字段，再进入预览。在 **Recipient emails**
中为同一人填写一个或多个邮箱，用逗号分隔。任一受邀邮箱通过验证码验证后，
签署一次即可完成这位签署人的签名；签名记录保留实际使用的邮箱。一次请求
的所有签署人合计最多填写 10 个邮箱。多位签署人仍需分别完成自己的字段，
之后才会生成最终文件。

### 检索的工作原理 {#how-retrieval-works}

检索是分块级别的混合检索，并通过 Reciprocal Rank Fusion 融合结果：

1. 文档被切分为约 1,600 字符的分块；每个分块拥有自己的嵌入向量（pgvector，由内置的 Ollama 服务生成）。
2. 一次查询会在分块上同时运行向量搜索和 trigram/词法搜索（CJK 安全），并辅以文件名匹配。
3. 结果按每篇文档保留最佳分块进行去重，再做排名融合，使精确词匹配和语义匹配都能浮现。

尚未完成索引的新上传文档，在显式限定范围的搜索中仍然可以被找到——运行时会在工作区或指定知识库范围内回退为直接读取文件。

### 全局搜索 {#global-search}

搜索栏（以及 `GET /api/v1/search?q=`）在任务、文档、Agent 和会话之间进行快速子串搜索，并遵循每个用户的文档和工作区权限。它是对 Agent 用于内容问题的语义 `rag` 检索的补充，而非替代。

## 数据隔离 {#data-isolation}

所有内容都限定在你的实体（组织）范围内，工作区边界在其中生效：Agent 只能看到它们被映射进入的工作区，工作区范围内的结果会按用户进行权限过滤。请保持工作区边界的清晰含义——不要把不相关的团队或客户混在同一个工作区中，除非他们有意共享 Agent、文档和记忆。
